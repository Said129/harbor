# Large music collections

Desktop's playlist database does not truncate stored membership or playback queues at 500 entries. Its M3U importer accepts up to 5,000 entries. The native implementation previously imposed 500 at several different layers, so increasing only the importer would still lose queued entries or reject reordering.

Playlist membership and added-time validation now use the document's existing 100,000-record envelope and retain its 16 MB encoded size limit. The Rust ordering bridge accepts the same membership count and 8,192-byte IDs as the native document. Duplicate, empty and NUL IDs remain rejected, and reordering retains the source's index arithmetic. Invalid writes preserve the previous document.

Playback admission and enqueue no longer silently trim the queue to 500. The complete original Desktop queue class is unchanged. Only the native adapter's queue/preview envelope expands to 100,000, and its encoded request/response budget becomes 16 MB. The default upcoming request covers the supplied queue rather than its first 500 members. Both generator and native program digest are updated together. The previously executed 610 comparisons for the unchanged original queue class are retained; this change does not claim to have re-executed them.

Two new native cases cover 5,000 stored tracks and a long ID through the actual ordering ABI, reopened persistence and failed-write retention; and the real playback model's complete 5,000-entry queue, selection after entry 500, next, prioritized enqueue and full upcoming order through Apple JavaScriptCore. The existing typed queue case is affected because its old assertion rejected 501 entries; that assertion now requires acceptance. One new Rust case covers the large ordering operation, restoration, oversized ID and membership envelope.

These native and Rust cases have not executed yet. The playback-model case uses a controlled audio engine and does not prove physical audio performance. The larger transport budgets are envelopes, not a guarantee that every possible 100,000-track document fits within 16 MB. Local audio-file library/folder scan limits, actual M3U import, full provider matching and physical performance remain open. No IPA is requested. The running cover/cache validation is pinned to its earlier source and does not contain these changes.

Five new boundary comparisons have executed successfully in Node against the unchanged original queue class and the expanded adapter: all 4,999 upcoming entries, next after index 750, end, repeat-all wrap and rejection above the adapter envelope. The old 610 comparisons were retained. The actual program SHA-256 is `224e1945b940bb26dabb04ffe9aea4761eb16e2de1fa61a8ba10245f71684718`; only the two adapter limits differ from the prior program. This is JavaScript evidence rather than Apple execution.

Local checks for the core, iOS bridge and Desktop Rust manifests cannot reach application compilation because this Windows environment lacks `link.exe`, needed by the compiler's dependency build scripts. Their actual failed outputs are retained under feature-specific names. Rust formatting and changed-file checks passed, but Rust type checking and the new unit case still need execution on the Apple host. No compiler-warning approval is inferred from an unavailable check.

The focused `music-export-large` selection now requests four new export cases, two new large-collection cases, the affected typed-queue case, the playlist mount with its new Export action and the repaired server-header mount. That is nine native cases and 12 original captures. The playlist mount receives an actual owned `MusicPlaybackSession` and loopback pairing so Export is enabled as it is on the normal Music page; it does not claim to navigate the Files picker. The Apple workflow separately checks the core and production bridge with warnings denied, then runs only the one new Rust ordering case. Original logs, input hashes and the exact Rust outcome must accompany the native results. A failure before native execution preserves the available compiler evidence. These requests and the successful local preflight are not execution results. The 46 approved unrelated nearby native cases and the original 610 queue comparisons are retained.
